## Per-sprint commentary

### Sprint 2 v2 — claude-2 pivot

The pivot itself. See `sprint_2_dispatch_brief_2026-05-07.md` for full scope. Five
parts:

- **A.** Tag claude-baseline + create claude-2 from main tip + bench backup.
- **B.** Reverse-direction features inventory (claude → main perspective).
- **C.** ADR 0001 ratified — adopt main's tick/sub as canonical pub/sub; no in-tree
  shim.
- **D.** mdata breakage report drafted (held internal until Sprint 3 starts).
- **E.** Roadmap rewrite (this file), retro, cadence_metrics row 2, sprints_index,
  CLAUDE.md branch policy rewrite, memory update.

**Why first:** the pivot is a one-time structural move; everything downstream depends
on it. No Rust ports happen here.

### Sprint 3 — additive feature port (wave 1)

**What ports.** Per Sprint 2 Part B inventory, the **additive** claude-only features
that don't conflict with anything on claude-2:

- Int64-quantized price storage + `set_column_scale` (golden rule 4) — load-bearing
  for mdata's HDB layout; must preserve dtype semantics on read.
- GIL-released `Engine::eval` (golden rule 5) — the 6.10× concurrent throughput
  win; must verify on claude-2 with a parallel Python harness.
- Structured exception hierarchy (`ChiliError` → `PepperParseError` / `PartitionError`
  / `TypeMismatchError` / `NameError` / `SerializationError`) (Phase 13 / WL 3.3).
- Logger built-ins (`.log.{info,warn,debug,error}`).
- mimalloc global allocator in chili-py cdylib.
- parse_cache invariants — verify claude-2's parse_cache (from upstream `9b65a50` +
  `2286dec`) hits at ≤ 385ns (golden rule 6); if not, port claude's tighter
  implementation.

**What doesn't port here.** Pub/sub re-implementation (Sprint 4); shape-divergent
features that need design decisions (`overwrite_partition` vs `write_partition(overwrite=…)`,
etc.); bench rebaseline (starts here, completes Sprint 5).

**Bench gates.** Each port that touches a hot path (`docs/bench/phase{1..7,9}.md`
shapes) gets a before/after run. Goal: claude-2 hits or exceeds claude-baseline
numbers.

**Tests.** Port claude's unit tests for each feature. Mdata-style integration tests
deferred to Sprint 5.

**Predicted: 10-15pp.** Roughly 1-2pp per port + 2-3pp bench-rebaseline scaffolding.

**Gate:** mdata sign-off on `docs/sync/mdata_breakage_report_2026-05-07.md` before
Sprint 3 starts. mdata stays on the existing claude-baseline wheel until Sprint 5
delivers the new wheel.

### Sprint 4 — feature port (wave 2) + pub/sub

**What ports.**

- Remaining shape-divergent features per inventory: case-by-case calls (most likely:
  use claude-2's main-derived shape, mark claude's for A/B benchmark archival).
- IF mdata's tp/rdb refactor needs them: re-implement claude's in-process Python
  `publish(ipc_bytes)` / `subscribe(callback)` on top of claude-2's tick/sub framework.
  Most likely outcome per ADR 0001: retire both, mdata refactors directly to
  `publish(table, df)`.
- Cross-process TCP `publish(handle, bytes)` — same retire-or-port call.

**Tests.** Rewrite tests for ported / retired features. Chili-py tests rewritten
for new shapes.

**Bench gates.** Same as Sprint 3 — A/B against `claude-baseline-2026-05-07`-built
binary on the parallel-binary methodology.

**Predicted: 8-12pp.** Lower than Sprint 3 because some claude-only features may
be deliberately-retired (no port work).

### Sprint 7 — bench-suite-v0 (STAC-M3 shape)

Per `q_kdb_landscape.md` §3, kdb+'s headline benchmark is STAC-M3. To set chili
optimization targets credibly, in-tree benchmark suite mirroring STAC-M3's operation
shape (NBBO, VWAB-D, VWAB-12D, MOHIBID, range scans).

**Out of scope:** running the actual STAC-M3 audited benchmark (requires
registration + audit + specific hardware). We're building an *equivalent shape*
for internal comparison.

**Deliverable:** `crates/chili-op/benches/stac_m3_shape/` + baseline numbers in
`docs/bench/stac_m3_shape_baseline.md`.

**Predicted: 5-8pp.**

### Sprint 8 — perf-pass-1

**Decomposition target** (per `shakti_analysis.md` §4.2): Shakti's 3-7× kdb+ edge
is ~30-40% storage-format / vectorization, ~30-40% primitive selection, ~10-20%
interpreter dispatch. Chili already has good interpreter dispatch (parse-cache
hit ≤ 385ns). Highest-ROI perf gains: primitive vectorization + storage codecs.

**Likely contents:**
- Audit chili-op operators for missed SIMD opportunities; tighten with explicit
  polars `.cast()` + `.alias()` chains where the compiler isn't inlining.
- Explore dictionary / delta / bitpack codecs for Int64-quantized columns
  (golden rule 4) — Polars supports these via Parquet stats; verify they're
  applied.
- Run STAC-M3-shape benchmark from Sprint 7 before AND after; document delta in
  `docs/bench/perf_pass_1.md`.

**Predicted: 6-10pp.**

### Sprint 9 — perf-pass-2 + KDB-X CE comparison

**Why now:** if KDB-X Community Edition has commodity-runnable bits available by
this date per `kdb_alternatives.md` §2.C.5, it's the closest apples-to-apples
baseline kdb+ has ever exposed (cores=24, threads=4, mem=16 GB, conns=8). Run
chili's STAC-M3-shape benchmark on the same hardware against KDB-X CE.

**Out of scope:** running KDB-X CE in production. Benchmark exercise only.

**Predicted: 6-10pp.**

### Sprint 10 — Pepper conformance to k9 design

Per `shakti_analysis.md` §4.3, k9 has converged on a smaller primitive set than q.
Pepper is currently q-shaped per CLAUDE.md ("`pepper` (q-like)"). For the
kdb+-replacement vision, Pepper should be evaluated against modern Whitney design
choices, not 1990s q.

**ADR territory.** Language-layer changes are user-visible — needs explicit user
direction.

**Predicted: 5-10pp.**

### Sprint 11 — deep housekeeping #2

Second 5-sprint sweep (count from Sprint 6). Same scope.

### Sprint 12 — perf-pass-3 + Iceberg eval

Per `kdb_alternatives.md` §3.2, Parquet+Iceberg is eating proprietary columnar
formats. Chili's HDB layout is already Parquet-native; growing Iceberg
compatibility (catalog metadata, snapshot management) is the additive step that
future-proofs chili in cloud-native deployments.

**Predicted: 6-12pp.**

## Sequencing principles applied

1. **Pivot first.** Sprint 2 v2 is the structural foundation; everything downstream
   depends on it.
2. **mdata unblock by Sprint 5.** Wheel ships then; mdata's refactor work runs in
   parallel during Sprints 3-4.
3. **Bench-driven optimization.** Sprints 5-7-8-9-12 all gate on having measurable
   baselines. No "felt faster" sprints.
4. **5-sprint housekeeping cadence enforced.** Sprints 6 and 11 are sweeps, not
   feature work, per `.claude/rules/sprint-cadence.md`.
5. **Strategic milestones explicit.** Sprint 10 (Pepper language) is an ADR sprint;
   the roadmap doesn't assume direction.
6. **A/B comparison via parallel binaries.** No in-tree shim; build from
   `claude-baseline-2026-05-07` tag and `claude-2` tip independently; compare metrics.

## What this roadmap is NOT

- **Not a guaranteed schedule.** Each sprint's pp band is calibrated against
  Sprint 1 actuals (~25pp research-heavy) and Sprint 2 v1's halt cost (~1.5pp);
  every prediction is wide. Halt-and-escalate criteria from the brief template
  apply per sprint.
- **Not a replacement for sprint dispatch briefs.** Each sprint here gets a real
  brief at kickoff.
- **Not exhaustive.** New sprints will be added based on findings and user
  direction. Specific candidates not yet sized:
  - kdb+ q→Pepper translator tool (chili-as-replacement story needs migration tooling)
  - chili-as-library distribution (pyproject.toml package boundary cleanup)
  - WebAssembly target (chili-wasm — speculative)
  - Iceberg catalog server (Sprint 12 follow-on if value confirmed)
