## Per-sprint commentary

### Sprint 2 — mdata-foundation

**Why first:** mdata is operationally blocked. Their wishlist's P0 #1 (`b20177c` TCP listener) is a clean cherry-pick (§2.4 of inventory). The serde9 nested-MixedList fix from `7948744` is orthogonal to the pub/sub portion and is a confirmed bug fix. `3aeee62`'s `stats()` method is a small additive feature with clean cherry-pick path.

**Out of scope here:** the bigger pub/sub work in `7948744` (the `init_tick` / DataFrame-based `publish` / `tick.pep` / `sub.pep` part) — that requires architectural reconciliation, not cherry-pick. Surface this back to mdata so they don't expect it from this sprint.

**Wishlist Section 3 validation gate:** `pytest crates/chili-py/tests/test_engine.py` is green (the 42 EngineState surface tests landed by `b20177c`). `pytest crates/chili-py/tests/test_tick_sub.py` is **not yet** green — it depends on the pub/sub bits we're explicitly deferring; surface this to mdata.

**Version bump:** `0.7.5 → 0.7.6-claude.1` per the wishlist's request for lockfile-detectable rebuild marker.

**Predicted: 5-8pp.** Calibrated against Sprint 1 actuals — Sprint 1 was research-heavy and landed at ~28-30pp; Sprint 2 is implementation-heavy with bounded scope, should be smaller.

### Sprint 3 — load-tree + multi-sub

**Why second:** mdata's Wave-3 5-level HDB layout (per `docs/proposals/load_tree_namespaced_hdb.md`) needs the recursive `load_par_df` from `aa227b3`. Multi-subscriber broadcast lets mdata attach ≥3 subscribers (rdb / archiver / signal) per the wishlist's stated topology.

**Conflict resolution work:** moderate. The recursive walker replaces claude's 2-level walker — same function, semantically extended. Multi-subscriber broadcast threads through `topic_map` writes. HandleOutOfRangeErr is purely additive. Estimated 2-3pp of merge work.

**Bench gate:** the recursive `load_par_df` change touches a hot path (`docs/bench/phase{N}.md` data is the baseline). Run `cargo bench -p chili-op load_par_df` before AND after; results land in `docs/bench/phase{N+1}.md`.

**Predicted: 4-7pp.**

### Sprint 4 — pub/sub ADR + reconciliation + A/B scaffolding

**Why this is one of the biggest sprints of the plan:** three competing pub/sub models on claude (per inventory §2.6) need to be reconciled into one. Without this, mdata cannot ship their target tp/rdb/archiver topology, and chili cannot claim a coherent "kdb+ tickerplant equivalent" surface.

**ADR options to weigh** (also captured in `inventory_2026-05-06.md` §2.6):
- (a) merge upstream's tick/sub framework as the canonical model; retire claude's Python `publish(ipc_bytes)` and engine `publish(handle, bytes)`.
- (b) keep claude's two models; port only the tplog durability contract from upstream as an additive layer.
- (c) hybrid: upstream's `tick.pep` / `sub.pep` as canonical Pepper-level; claude's Python `publish(ipc_bytes)` retained as low-level escape hatch for in-process callers.

**Decision (user direction 2026-05-07): Option (c) with measured retirement.** Sprint 4 implements the hybrid as the *transitional* state — NOT as a permanent fixture. The right to retire claude's models is earned via A/B data in Sprint 4.5, not declared up-front.

**Sprint 4 deliverables:**
- `docs/decisions/0001-pub-sub-canonical-model.md` — first chili ADR under the new cadence, recording the Option (c)-with-measured-retirement decision.
- Implementation of upstream's tick/sub framework (tplog write + broker publish, `tick.pep` / `sub.pep`, `init_tick` / `publish(table, df)`) alongside claude's existing models.
- A/B benchmark scaffolding — a deterministic test harness that exercises both pub/sub paths with comparable workloads (msg/s, subscriber counts, payload sizes). The harness is durable infrastructure that will outlive the retirement decision.

**Predicted: 10-16pp** (bumped from 8-14 to reflect the A/B-scaffolding addition).

### Sprint 4.5 — pub/sub A/B measurement + mdata feedback

**Why this exists as its own sprint:** the A/B comparison + mdata's production-audience feedback need to be a real measurement window with proper time, not a Sprint 4 afterthought. mdata is the *only* current production user of claude-branch's pub/sub; their dogfood feedback is irreplaceable.

**Sprint 4.5 deliverables:**
- Run the A/B benchmark suite under realistic load (commodity hardware, N-subscriber scaling). Document results in `docs/bench/pub_sub_ab_<date>.md`.
- Solicit mdata's structured feedback on both surfaces — ergonomics, surprises, missing features. (User-coordinated; chili can't autonomously dispatch mdata work.)
- `docs/decisions/0002-pub-sub-retirement-call.md` — second ADR; takes the data + feedback as inputs, recommends retire-claude / retire-upstream / keep-hybrid-durably, and gates Sprint 8's full-merge work accordingly.

**Predicted: 4-7pp.** Bench-run + ADR-write; modest unless retirement requires actual code removal (in which case spill into Sprint 5 or 6).

**Cross-references:** axis definitions and retirement-gate criteria in `inventory_2026-05-06.md` §2.6.

### Sprint 6 — bench-suite-v0

**Why now:** per `q_kdb_landscape.md` §3, kdb+'s headline benchmark is STAC-M3. To set chili optimization targets credibly, we need an in-tree benchmark suite that mirrors STAC-M3's operation shape (NBBO, VWAB-D, VWAB-12D, MOHIBID, etc.) and can be run on commodity hardware.

**Out of scope:** running the actual STAC-M3 audited benchmark — that requires registration + audit + specific hardware. We're building an *equivalent shape* for internal use.

**Deliverable:** `crates/chili-op/benches/stac_m3_shape/` with one Criterion benchmark per major STAC-M3 operation; baseline numbers reported in `docs/bench/stac_m3_shape_baseline.md`.

**Predicted: 5-8pp.**

### Sprint 7 — perf-pass-1

**Decomposition target** (per `shakti_analysis.md` §4.2): Shakti's 3-7× kdb+ edge is ~30-40% storage-format / vectorization, ~30-40% primitive selection, ~10-20% interpreter dispatch. Chili already has good interpreter dispatch (parse-cache hit ~385ns). Highest-ROI perf gains for chili: primitive vectorization + storage codecs.

**Likely sprint contents:**
- Audit chili-op operators for missed SIMD opportunities; tighten with explicit polars `.cast()` + `.alias()` chains where the compiler isn't inlining.
- Explore dictionary / delta / bitpack codecs for Int64-quantized columns (golden rule 4) — Polars already supports these via Parquet stats; verify they're being applied.
- Run STAC-M3-shape benchmark from Sprint 6 before AND after; document delta in `docs/bench/perf_pass_1.md`.

**Predicted: 6-10pp.**

**Pre-conditions:**
- Sprint 4 ADR ratified and shipped.
- chili-pie / chili-sauce naming reconciled (action item from inventory §2.9).
- All remaining upstream commits not yet picked up are reviewed.
- CLAUDE.md branch policy section may need rewrite (today: "no remote, claude only" — post-merge: ?).

**Predicted: 8-14pp.** Big merge resolution + branch-policy decision + CLAUDE.md rewrite.

### Sprint 9 — deep housekeeping #2

Second 5-sprint sweep. Same scope as Sprint 5.

### Sprint 10 — perf-pass-2 + KDB-X CE comparison

**Why now:** if KDB-X Community Edition has shipped commodity-hardware-runnable bits by Sprint 10, it's the closest apples-to-apples baseline kdb+ has ever exposed. Per `kdb_alternatives.md` §2.C.5, KDB-X CE caps are `cores=24, threads=4, mem=16 GB, conns=8` — well within commodity laptop / cloud-VM envelope. **Run chili's STAC-M3-shape benchmark on the same hardware against KDB-X CE.** Publish results.

**Out of scope:** running KDB-X CE in production. This is a benchmark exercise.

**Predicted: 6-10pp.**

### Sprint 11 — Pepper language conformance to k9 design

**Why:** per `shakti_analysis.md` §4.3, k9 has converged on a smaller primitive set than q. Pepper is currently q-shaped per CLAUDE.md ("`pepper` (q-like)"). For chili to pursue the kdb+-replacement vision, Pepper should be evaluated against modern Whitney design choices, not 1990s q.

**ADR territory.** Language-layer changes are user-visible — needs explicit user direction.

**Predicted: 5-10pp.**

### Sprint 12 — perf-pass-3 + Iceberg eval

**Why:** per `kdb_alternatives.md` §3.2, the Parquet+Iceberg pattern is eating proprietary columnar formats. Chili's HDB layout is already Parquet-native; growing Iceberg compatibility (catalog metadata, snapshot management) is the additive step that future-proofs chili in cloud-native deployments.

**Predicted: 6-12pp.**

## Sequencing principles applied

1. **mdata unblock first.** Sprints 2-4 prioritize the wishlist surface even though Sprint 4 is heavy. mdata is operationally blocked; competitive-position work waits.
2. **Bench-driven optimization.** Sprints 6-7-10-12 all gate on having measurable baselines before claiming wins. No "felt faster" optimization sprints.
3. **5-sprint housekeeping cadence enforced.** Sprints 5 and 9 are sweeps, not feature work, per `.claude/rules/sprint-cadence.md`.
4. **Strategic milestones explicit.** Sprint 8 (main-merge) and Sprint 11 (Pepper language) are user-decision sprints; the roadmap doesn't assume their direction.

---

## What this roadmap is NOT

- **Not a guaranteed schedule.** Each sprint's pp band is calibrated against Sprint 1 actuals, but every prediction is wide. Halt-and-escalate criteria from the brief template apply per sprint.
- **Not a replacement for sprint dispatch briefs.** Each sprint here gets a real brief at kickoff; this file is sequencing.
- **Not exhaustive.** New sprints will be added based on findings and user direction. Specific candidates not yet sized:
  - kdb+ q→pepper translator tool (chili-as-replacement story needs migration tooling)
  - chili-as-library distribution (pyproject.toml package boundary cleanup)
  - WebAssembly target (chili-wasm — for browser-side analytics; speculative)
  - Iceberg catalog server (if Sprint 12 finds value, follow-on)
